Migración incremental de `client/src/context/*` a **Redux Toolkit** (estado de cliente) + **TanStack Query** (estado de servidor), documentada fase por fase en [plans/redux-toolkit-react-query-migration.md](plans/redux-toolkit-react-query-migration.md).

**Por qué:** el usuario hace este cambio como práctica dirigida — su trabajo de oficina (proyecto separado, NO Turnocero) le pide arquitectura MVC-ish + Redux Toolkit y quiere aprenderlo en un sandbox real sin arriesgar nada. Turnocero es hobby/solo-dev, así que la migración es opcional/de aprendizaje, no una necesidad estructural del proyecto (ver conversación 2026-07-29 — la arquitectura Context+reducer previa ya era adecuada para su escala).

**Decisión de arquitectura clave:** NO se adoptó RTK Query — se usa **TanStack Query** (`@tanstack/react-query`) por separado para todo lo que sea estado de servidor (los 102 archivos con `axios.` directo), y Redux Toolkit solo para estado de cliente real (UI, preferencias, flags). Cada uno de los 7 contextos se clasificó explícitamente en la tabla del plan antes de migrar — varios (`SiteConfigContext`, la lista de `NotificationContext`) resultaron ser casi 100% server state y NO necesitan slice de Redux, solo queries.

**Convivencia, no big-bang:** `ReduxProvider` + `QueryClientProvider` envuelven el árbol de providers existente en [client/src/App.jsx](client/src/App.jsx) desde la Fase 0; los Context viejos se borran uno por uno solo cuando su reemplazo ya está mergeado y verificado.

**Regla transversal del plan:** cada fase cierra solo después de un checklist de verificación exhaustiva (suite verde + recorrida manual end-to-end + ambos temas + ambos idiomas + consola limpia + comparación explícita antes/después) — el criterio es "la app queda igual o mejor", no solo "no rompió nada".

**Estado de fases** (actualizar acá al cerrar cada una — ver detalle y fecha de cierre en el plan):
- ✅ Fase 0 — Setup (`@reduxjs/toolkit`, `react-redux`, `@tanstack/react-query` instalados; `client/src/store/store.js`+`hooks.js`; `client/src/queries/queryClient.js`; providers envueltos en `App.jsx`; devtools en dev). Cerrada 2026-07-29.
- ✅ Fase 1 — POC Redux Toolkit puro (Theme + Language). `store/slices/{theme,language}Slice.js` (createSlice + `createListenerMiddleware` para side effects) + hooks públicos en `hooks/{useTheme,useLanguage}.js`; `ThemeContext.jsx`/`LanguageContext.jsx` eliminados. Cerrada 2026-07-30.
- ✅ Fase 2 — POC TanStack Query puro (Noticias). `queries/noticias.js`: `useNoticiasQuery` terminó siendo `useInfiniteQuery` (portada usa "cargar más" acumulativo, no page number) + `useNoticiaQuery`/`useRelatedNoticiasQuery` (query dependiente)/3 mutaciones con `invalidateQueries`. `AllProviders.jsx` gana un `QueryClient` nuevo por render (`retry:false`) — patrón de referencia para cualquier test que use `useQuery`. Cerrada 2026-07-30.
- ✅ Fase 3 — NotificationContext (sockets). El plan original sobreestimaba el trabajo: NO se creó ningún slice de Redux (las refs `activeTableRef`/etc. no son state reactivo, no van a Redux) y `notificationReducers.js` (1096 líneas) + los 13 hooks de `notificationListeners/` no se tocaron — todos llaman `setNotifications((prev) => …)`, alcanzó con redefinir esa función en `NotificationContext.jsx` para que escriba a `queryClient.setQueryData` en vez de `useState`. `queries/notifications.js#useNotificationsQuery` es cache-only (`enabled:false`, sin queryFn real, "Query as a store") — el boot fetch volvió a un `useEffect` explícito porque un queryFn que fetchea+mergea tiene una race real (commit tardío pisa un markRead/socket más nuevo); el fix es mergear con la forma funcional de `setQueryData`, no leyendo `getQueryData` aparte. Gotcha de testing: `setQueryData` notifica por microtask, no sincrónico en `act(() => click())` — cualquier test post-acción necesita `await waitFor()`. Cerrada 2026-07-30 — detalle completo en el plan.
- ✅ Fase 4 — SiteConfigContext. Sin Redux, sin `useMutation` (PanelAdmin ya maneja su propio busy/error local). Reto real: replicar el reset optimista de `retryConnection` (splash de vuelta al reintentar) — `isPending` no sirve (queda `false` para siempre tras el primer settle, incluso durante un refetch), la solución fue `loaded = !isFetching` + `backendDown = !isFetching && !!error && isBackendDown(error)`. Bug de aislamiento de tests descubierto (preexistente, recién expuesto): `App.test.jsx` renderiza `<App/>` 3 veces con el `queryClient` singleton de producción — sin `queryClient.clear()` en `beforeEach`, `staleTime:Infinity` hacía que el test del 500 reusara cache de tests anteriores. Aplica a cualquier test futuro que monte `<App/>` completo más de una vez. Cerrada 2026-07-30.
- ✅ Fase 5 — CommunityContext + ChatContext. Otra vez sin slice de Redux (`openOrder`/`minimized` de chat ya eran reactivos vía Context, un solo dueño natural — mismo criterio que las refs de Fase 3). `conversations` de chat usa el mismo patrón cache-only de `notifications` (shim soporta updater funcional Y valor directo). `CommunityContext` con 2 queries independientes (`mias` + `tenant`); `viewingVersion` queda local. Insight nuevo: `loaded` de Community usa `isPending` (no `isFetching` como SiteConfig en Fase 4) porque su `reload()` es un refresh silencioso en 2do plano, no un retry visible — cada context necesitó evaluación propia de qué significaba "loaded" ahí. Gotcha de lint: `data?.x ?? []` crea array nuevo cada render sin datos, invalida `useMemo` río abajo — usar constantes module-level `EMPTY_X` en vez de literales. Cerrada 2026-07-30 — detalle completo en el plan.
- ✅ Fase 6 — Migración masiva de los 102 axios ad hoc, dominio por dominio (mesas → torneos → eventos → compartidas → bg-watch → usuarios → mathtrade/comunidades-admin). Cerrada 2026-08-03. **mesas cerrado** 2026-07-30 (11 archivos): `queries/tables.js` + `queries/bgg.js` (autocomplete compartido MesaForm/CreateTable) + `queries/youtube.js` (`useTableTutorialsQuery`, TableTutorials quedó sin ningún hook propio). Mismo patrón cache-only de Fases 3/5 para `TableChat` (mensajes + socket propio); Comments/Ratings usan `useQuery` real (GET idempotente sin socket, no cache-only). Insight nuevo: `TableDetail` necesitó un `blockedPrivate` derivado explícito — con Query los datos llegan al cache aunque el server permita verlos (regla de negocio del cliente restringe más que el server), así que el criterio viejo de "no llamar setState y listo" no alcanza, hay que bloquear el render explícitamente. Geocode y detalle de juego BGG elegido quedaron en axios directo (uso único, sin beneficio de cache). Sin Redux. **torneos cerrado** 2026-07-30 (12 de 20 archivos — el resto son presentacionales sin axios): `queries/torneos.js` con `torneoKeys` anidadas bajo `detail(id)` (matches/standings/groups(phase)/nextPhasePreview) — un solo `invalidateQueries({queryKey: torneoKeys.detail(id)})` en `TorneoDetail.refresh()` refresca en cascada todo lo que cuelga del torneo, sin enumerar cada sub-query. `useTorneosQuery` es `useInfiniteQuery` (mismo patrón "cargar más" de Noticias, Fase 2). `useUserSearchQuery` (para `AddParticipantModal`, admin_only inscription) vive en torneos.js por ahora — candidata a mudarse a `queries/users.js` cuando se migre el dominio usuarios. Insight nuevo: cuando un componente tiene tanto una query de lectura (preview/búsqueda) como una mutación de escritura (submit/add) y ambas necesitan mostrar error en el mismo lugar, no forzar los dos a un único `useState` — usar una constante derivada `error = queryIsError ? tError : submitErrorState` (visto en `PhaseTransitionModal` y `AddParticipantModal`). Sin Redux. **eventos cerrado** 2026-08-02 (4 de 7 archivos con axios: Eventos, EventoDetail, EventoInscripciones, EventoLudotecaPicker; EventoForm/EventoLudoteca/EventoMesas/useEventoSocket sin cambios): `queries/eventos.js` con `eventoKeys` anidadas bajo `detail(id)` (mismo patrón que `torneoKeys`). `useEventosQuery` (lista) es `useInfiniteQuery`; sus 4 socket handlers parchean la forma `{pages: [...]}` directamente (map/filter cross-page para updates/counts/deletes, `pages[0]` con dedupe por `_id` para el prepend-on-create). Insight nuevo: la ludoteca y las mesas del evento no tienen GET propio idempotente en todos los casos — son sub-listas embebidas/derivadas — así que se modelaron como query cache-only (`enabled:false`) sembrada una vez por `id` vía `useEffect` con dep `!!evento` (booleano, no la referencia del objeto) para no re-sembrar en cada patch posterior de socket. Patrón nuevo (`forcedGone`): cuando un socket necesita forzar un estado derivado de `isError` (ej. "evento borrado" sin esperar 404) y no se puede escribir el estado de error de una query a mano, usar un booleano local OR'd al derivado (`const notFound = isError || forcedGone`). Sin Redux. - ✅ Fase 7 — AuthContext (más riesgosa, al final a propósito). Cerrada 2026-08-03. `authSlice.js` (nuevo) guarda `{token, viewAsUser}`; a diferencia de theme/language (initialState bakeado, alcanza con correr una vez por import), acá el valor inicial depende de `localStorage` por caller, así que se expone `getInitialAuthState()` como getter aparte, pasado vía `configureStore({preloadedState})` en cada call site (`store.js` real + `makeStore()` de test) — también sincroniza el header de Axios de entrada. `queries/auth.js` (nuevo): `useMeQuery({enabled})` + 9 funciones planas. `AuthContext.jsx` se reescribió por dentro pero **mantiene el mismo Provider/Context** — contrato público de `useAuth()` (15 campos, 65 consumidores) intacto; internamente ahora es Redux+Query. Bug real encontrado (no solo timing): la limpieza de token inválido al bootear se re-disparaba en cualquier 401 posterior de `/me` — incluido el que la propia query dispara al pasar de `enabled:false` a `true` justo tras un login recién exitoso, pisando el token nuevo. El original solo corría esa limpieza una vez (efecto de boot `useEffect(() => {}, [])`); con `useMeQuery` viva toda la sesión hubo que replicar el "una sola vez" a mano con un `useRef(token)` capturado en el mount y anulado tras el primer uso. Suite completa verde (299/299 archivos, 2969/2969 tests). Verificado en browser con sesión real: login, logout, view-as-user (persiste tras reload vía `preloadedState`), registro (sin token), forgot-password, botón OAuth Google sin errores, SSO de subdominio (`?tenant=` sin token dispara `/me` igual). Limitación de entorno (no de código): verificar-email y reset-password terminan en un código/token por email real que no se puede completar sin la bandeja de entrada — riesgo bajo porque comparten patrón exacto con login/oauthLogin (sí verificados) y el bug real encontrado los afectaba a los tres por igual. Pregunta abierta para Fase 8: el punto "borrar `context/AuthContext.jsx`" del plan no aplica tal cual — acá se decidió mantener el Context por el radio de 65 archivos, a diferencia de Theme/Language que sí se eliminaron en Fase 1; definir con el usuario antes de tocarlo. Detalle completo en el plan.
